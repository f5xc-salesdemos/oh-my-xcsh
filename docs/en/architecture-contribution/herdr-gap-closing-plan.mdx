## Which invariants define parity?

Three planes remain separate:

1. **Herdr tracked execution** owns process admission, pane visibility, output drainage, exit/signal, cancellation request, and restart loss. It never translates exit zero, TUI idle, output silence, pane cleanup, or shutdown into semantic success.
2. **XCSH semantic turns** own start, progress, waiting for input/approval, successful completion with bounded result, failure, cancellation, interruption, and continuation/fork identity.
3. **Control Manager acceptance** owns durable task state, required-child aggregation, replay, supersession, delivery acknowledgment, and correlation of a visible response with the accepted result.

Canonical identity is `(producer, session_id, turn_id, generation)`. The native persisted XCSH session supplies `session_id`. XCSH creates and persists `turn_id` before the first event and retains it across reconnect. `generation` distinguishes deliberate continuation/retry that supersedes older work. Pane/execution IDs are provenance, not semantic identity.
Manager task association must be validated against server-owned pane/execution context; a free-form client task ID is not trusted alone.

Events have a monotonic sequence/revision, state, timestamp, and optional bounded safe payload. Exact replay with the same identity, revision, and digest is idempotent; changed content at the same revision conflicts; older revisions cannot regress state. Terminal state is immutable, while a new generation may explicitly supersede it.
Restart replays persisted events; unrecoverable active work becomes `interrupted`/`lost`, never `completed`.

## What do statuses mean?

| State | UI and Manager meaning | Required evidence |
| --- | --- | --- |
| `starting` | Turn identity is durable; work has not begun. | Created once before model/tool work. |
| `working` | Turn is actively progressing. | May emit rate-limited progress or enter a wait. |
| `waiting_input` | Human input/approval is required; neither failure nor completion. | Bounded safe reason; resumes to working or terminates by cancel/failure. |
| `completed` | Native semantic settlement succeeded with a bounded result. | Emitted only after agent-end settlement, never inferred from idle/exit. |
| `failed` | Semantic turn ended unsuccessfully. | Bounded safe reason; partial output cannot appear as success. |
| `cancelled` | Requested cancellation reached terminal semantic state. | A cancellation request alone is not terminal evidence. |
| `interrupted` / `lost` | Outcome cannot be proven. | Never success; requires continuation/retry or operator resolution. |
| execution `exited` | Host process stopped; output drained or marked incomplete. | Process-only evidence, displayed separately from turn/task outcome. |

UI surfaces show process state, semantic turn state, and feature acceptance independently. Display metadata may mirror safe status but is never an authoritative completion input.

## What end-to-end tests are required?

Every scenario traverses **Control Manager request → Herdr tracked execution → XCSH semantic events → Herdr durable turn journal → Manager journal/outbox/direct acknowledgment → correlated Manager response**, asserting semantic and process state separately.

| Scenario | Required assertion |
| --- | --- |
| Simple success | Stable identity reaches `completed`; bounded result/digest survive pane cleanup and are acknowledged once. Exit remains separate. |
| Failure | Native failure reaches `failed`; output or exit zero cannot convert it to success. |
| Input/approval wait | Wait stays nonterminal through idle, resumes on the same turn, then completes/fails; parent remains incomplete while waiting. |
| Cancellation | Request, signal, and terminal semantic cancellation are distinct; no completion appears. |
| Continuation | Same session, new turn/generation; prior result remains queryable and is not redelivered. |
| Reconnect | Disconnect before acknowledgment causes replay; exact duplicate is idempotent and correlated response arrives once. |
| Pane cleanup | Cleanup preserves execution, semantic result, Manager journal, and pending acknowledgment. |
| Component restart | Restart each component at defined cut points; terminal data replays and unrecoverable active work becomes interrupted/lost. Record retention/tombstone limits. |
| Duplicate/conflict/order | Exact duplicate succeeds idempotently; changed digest at same revision conflicts; stale events cannot regress state; newer generation supersedes without erasing audit. |
| Resume/fork | Resume path/ID retains session identity; fork has distinct lineage and cannot collide. |
| Protocol mismatch | Supported capabilities work; unsupported/missing capability fails visibly before tracking is claimed. |
| Aggregate completion | Only all-required evidence permits acceptance; failed, waiting, missing, or deferred required items keep it incomplete. Optional items do not block/reopen core. |

Unit tests use deterministic clocks, persistence reopen, injected disconnects, and schema fixtures. Integration uses real local binaries with temporary state. Staged UAT uses an isolated Herdr environment before default. Live evidence records artifact hashes, capabilities, execution/session/turn IDs, revisions/digests, acknowledgments, and aggregate status without secrets/full transcripts.

## What decisions and risks need review?

- **Recommended:** first-class durable Herdr semantic-turn journal; metadata cannot carry results, ordering, or restart guarantees.
- **Recommended:** explicit capabilities and supported protocol set/range; accepting every newer version risks schema misinterpretation.
- **Recommended:** server-bind task identity through execution/pane provenance and correlate Manager generation; do not trust free-form producer identity.
- **Recommended:** immutable terminal events and new generations for continuation/retry.
- **Risk:** current Herdr source is a dirty development worktree and installed binary lacks source provenance. Do not promote inspection to deployed evidence.
- **Risk:** nonfatal reporter errors preserve XCSH use but hide tracking loss. Show degraded tracking and fail Manager acceptance closed.
- **Risk:** retention/restart timing creates evidence gaps. Persist truncation/completeness/loss markers and block acceptance when evidence is missing.
- **Risk:** cancellation races completion. Serialize final revision acceptance; audit later conflicts without changing the accepted result.
